Is this person here, now?

Multi-factor, not multi-check.

A passphrase and a recovery code are both things you know: whoever learned one has usually learned the other from the same place. The classification is the point — Policy{Count: 2, DistinctKinds: true} is what two-factor is normally taken to mean, and two passphrases never satisfy it.

🔑

A key over any transport

fido speaks CTAPHID, GetInfo, MakeCredential, GetAssertion, ClientPIN. A Transport moves 64-byte reports; where they come from is somebody else's problem.

⏱️

One-time codes, replayed once

totp is RFC 6238 with the refusal the RFC requires: a code is valid for a whole step, so the verifier must reject a second use — and every step up to the last accepted.

⚖️

A policy that counts by kind

mfa decides how many factors, of which kinds, and what to say when some refuse. A factor that could not be asked has not failed, and there is no default policy.

🖥️

The platform's own factors

go-macos/factors gives Touch ID, go-gnulinux/factors the key over hidraw, go-mswin/factors Windows Hello. Neither Hello nor Touch ID is FIDO — which is why kinds are counted.

🧪

Proven against a real key

Registered, asserted, and the signature verified with the public key the key itself handed out. A COSE key could not verify anything if its extent were wrong by a byte.

📖

The reference was read first

libfido2 and the CTAP spec read as documentation. That caught two faults a key would never have shown: CTAPHID_KEEPALIVE is not an answer, and the message limit is the framing's.

Who is this person, and what would prove them?

What proves somebody is not one thing.

That used to be an assertion on this page. It is a measurement now: go-fileshare/fileshare serves one set of people over five protocols out of one directory, and asks a different question of each person for each one.

Serving a person overneeds, from their directory entry
SMBNTHash — NTLMv2 works from the password or its MD4(UTF16LE(password))
S3Password, the secret itself: SigV4 proves possession by computing an HMAC from it
WebDAVVerifier or Password — a source that can only check one is enough
SFTPPublicKeys, or a trusted user CA
NFSa Kerberos ticket — not a directory credential at all

SMB and S3 are the pair worth reading twice. Neighbours, not copies: an identity holding only an NT hash serves SMB and cannot serve S3, because an HMAC cannot be computed from an MD4. So directory carries what proves somebody, over a database (sqldir), an LDAP server (ldapdir) or a file (hcldir) — and authnd serves it back out over LDAP, because almost everything speaks LDAP.

Both halves

Kerberos is two halves, and they are two repositories.

🎫

kdc issues

AS-REQ and TGS-REQ over UDP and TCP, backed by the same directory, judged by MIT's own kinit and kvno with no MIT KDC in the loop. Only a source holding the password can back a realm: a KDC decrypts the pre-authentication, and a verifier answers a yes, not a key.

🛡️

krb5 accepts

An AP-REQ verified against a keytab and answered with the AP-REP gokrb5 will not build — without which a GSS-API client asking for mutual authentication completes no context at all. It signs and seals too, so sec=krb5, krb5i and krb5p.

Keeping them apart is the point: a service that only accepts tickets should not link a KDC. The acceptor has consumers outside this organisation — fileshare serves a disk image over NFS with sec=krb5, and go-filesystems/nfs links it directly one layer below. That matters because NFSv3 on its own proves nothing: AUTH_UNIX is a claim the client makes about itself, and a ticket is not.

Judged by something that is not this code.

OpenLDAP's own ldapsearch reads the server and is refused with Invalid credentials (49) for a wrong password and for the empty one. MIT's own kinit takes the tickets. A fixture built from one reading of a protocol can only ever confirm that reading.
