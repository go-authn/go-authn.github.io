Two questions,
and they are not the same.

Is this person here, now? is not who is this person, and what would prove them? go-authn answers both — the factors that prove presence, the directory that carries what proves each person rather than a password field, and both halves of Kerberos. Pure Go, CGO_ENABLED=0, and it builds for every one of the 47 targets the Go toolchain lists. BSD-3-Clause.

It says who it would serve, and who it never could.

authnd check opens every source — the file, the database, the other directory — and prints who would be published, what each person can prove, and who a Kerberos realm could issue a ticket to, without listening and without printing a secret — and, since v0.11.0, which standard object classes each entry will carry. Why go-authn

Multi-factor, not multi-check — and a directory that knows the difference.

A passphrase and a recovery code are both things you know: whoever learned one has usually learned the other from the same place. Requiring both buys far less than the count suggests.

🔑

A key over any transport

fido speaks CTAPHID, GetInfo, MakeCredential, GetAssertion, ClientPIN. A Transport moves 64-byte reports; where they come from is somebody else's problem.

⚖️

Counted by kind

Policy{Count: 2, DistinctKinds: true} is what two-factor is normally taken to mean, and two passphrases never satisfy it. A factor that could not be asked has not failed.

🗂️

What proves somebody is not one thing

SMB needs an NT hash; S3 needs the password itself, because SigV4 computes an HMAC from it. An identity holding only the hash serves one and cannot serve the other — so directory carries what proves each person.

🎫

Both halves of Kerberos

kdc issues, krb5 accepts — two repositories, so a service that only accepts tickets does not link a KDC. It signs and seals too, which is what krb5i and krb5p are.

🎓

Every university, one login

bridge is an OpenID Connect provider in front of RENATER or eduGAIN, through saml: an identifier from outside a university's own scope is dropped, and an assertion nobody signed is never read.

🖥️

The platform's own factors

Touch ID, a key over hidraw, Windows Hello — each an mfa.Factor, so a policy never learns which one it got.

🚫

Revocation that arrives, or fails closed

bridge signs and dates its KRL and CRL; authn-revokd verifies each before a server reads it, keeps the newest across restarts, and, when a list lapses, writes one that revokes the CA itself, so sshd refuses rather than trusting a stale list. Nothing in between is trusted: a mirror can delay a list, never forge or roll one back.

⚖️

Judged by other people's tools

OpenLDAP's own ldapsearch reads the server; MIT's own kinit takes the tickets. A fixture built from one reading of a protocol can only confirm that reading.
